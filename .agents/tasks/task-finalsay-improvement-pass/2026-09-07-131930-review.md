# Honest-metrics improvement pass on FinalSay (P1–P6) (v1)

This pass replaces FinalSay's headline time-to-identify number — previously hardcoded to a scan cost of 1.0 under an explicit "perfect retrieval" idealization — with a value measured by replaying the real retrieval algorithm, and it hardens the surrounding evidence: a real HF NLI run recorded next to the mock, a committed results artifact, an end-to-end smoke test, a live Postgres verification, and cleanup of the fake Alerts control plus a diversified benchmark. The central question for this review is integrity: was any number inflated, tuned, or cherry-picked to survive the switch from assumed to measured? The answer is no. The old ~19x claim is gone; FinalSay's saving-vs-chronological drops to a measured 1.46x (temporal) / 1.89x (institution), with retrieval recall@5 of 0.714 / 0.810 reported alongside, and those worse numbers are printed, committed, and documented as-is. Seed fixtures were untouched, so the rank was not gamed; the held-out temporal F1 stays 0.048 and kappa stays 0.625, confirming the benchmark diversification did not contaminate the eval.

Watch for: (1) the P1 retrieval mirror scores raw un-redacted notice text on both sides, whereas production `retrieve_candidates` scores redacted/extracted fields — a faithful mirror of the *algorithm* over *idealized inputs*, not the live pipeline's inputs (likely); (2) the measured-vs-chronological test still hard-asserts the favorable direction (`finalsay_cost <= chrono_cost`, `saving >= 1.0`) despite a docstring claiming it "records the true relationship rather than being tuned" (confirmed, minor); (3) `--report-all` with the HF stack absent overwrites the committed `docs/eval-results.md` and drops the real HF blocks in favor of a "NOT EXECUTED" note (confirmed, reproducibility footgun).

**Verdict**: APPROVED

## High-level view

The P1 change is the load-bearing one and it holds up. `time_to_identify` no longer assigns FinalSay a flat cost of 1.0; it calls a new `retrieval_rank` that reimplements `services.comparison.retrieve_candidates` against the fixture officials (same-institution filter, Jaccard over `[a-z0-9]+` tokens of length >2, +0.1 audience boost, top-K=5) and uses the applicable official's 1-based rank as the scan cost. Retrieval misses are charged the full institution-feed length rather than dropped, so a miss makes the number worse, never free, and recall@k is reported so a reader sees how often retrieval actually finds the notice. The one caveat is input fidelity: the mirror scores the raw gold `text` on both submission and official sides, while production scores redacted+extracted field text, so the measured rank tracks the real algorithm over cleaner inputs than the live path sees.

The HF path (P2) was genuinely executed once per split and recorded next to the mock, with runtime and setup noted. The strongest integrity signal in the whole pass is that HF is reported as *worse* than mock on the institution split (F1 0.289 vs 0.739) and trailing the nli/prompted_llm baselines there — nobody tuning for a favorable story invents that. Mock stays the zero-setup default: `requirements.txt` is untouched, the transformers/torch import is lazy inside the HF path only, and the cache is gitignored.

The results artifact (P3) emits the full six-metrics × five-systems × both-splits table to `docs/eval-results.md`, regenerated after P1/P2. Its `--report-all` path refuses to fabricate HF numbers when the stack is missing, writing an explicit "NOT EXECUTED" note instead — good, except that same path would clobber the committed real HF blocks if run in this sandbox.

The smoke test (P4) drives the real ASGI app through the whole journey — auth, publish, submit, redaction-before-storage, retrieval, gated classification, evidence trail, Merkle build/verify with a tamper flip, and an ambiguous→unresolved case — with assertions that would fail on regression rather than asserting static constants. It runs in-process rather than against a live uvicorn because the sandbox reaps background daemons between calls; that trade-off is documented and reasonable, though it does not exercise a real wire path.

The Postgres verification (P5) is honest: it records a real podman container run (schema via `create_all`, idempotent seed, a targeted `pg_smoke` script exercising submit/classify and provenance), and plainly states the limitations — no compose runtime in the sandbox (direct `docker run` substituted), containers don't persist across calls, and the pytest suite stays pinned to SQLite. Nothing is claimed to work that wasn't run.

The cleanup (P6) removes the localStorage subscription toggles from the Alerts page, leaving a clearly-labelled read-only preview with no interactive-but-fake control. The benchmark grows to 308 deterministically balanced pairs (44 × 7 labels) with per-index diversified display phrasing that lives only on `BenchmarkPair` rows; it never feeds the eval or kappa, so held-out F1 (0.048) and kappa (0.625) are unchanged, proving no contamination.

### Time-to-identify: from assumed 1.0 to measured retrieval rank

The old code assigned `costs = [1.0 for _ in held_out]` behind a comment openly calling it an idealization of perfect retrieval. That is gone. `time_to_identify` now, for the `finalsay` system, calls `retrieval_rank(g, officials)` per held-out pair and uses the returned 1-based rank as the scan cost; on a miss (`rank is None`) it appends `float(feed_len)` — the number of officials in the pair's institution — so an un-retrieved notice costs a full-feed scan rather than being silently excluded. `retrieval_recall_at_k` = hits/len is surfaced in the result dict, the printed report, and `docs/eval-results.md`.

`retrieval_rank` reimplements `retrieve_candidates` faithfully: same institution filter, `_retrieval_tokens`/`_retrieval_overlap` are byte-identical to `services.comparison._tokens`/`_overlap` (the `[a-z0-9]+`, length>2 rule and the Jaccard formula), the +0.1 audience boost, `top_k=TOP_K` imported from the service, and deterministic tie-breaking by external_id ascending. Running the harness reproduces the committed numbers exactly: temporal finalsay mean 13.238 vs chronological 19.286 (saving 1.457, recall@5 0.714); institution 9.429 vs 17.857 (saving 1.894, recall@5 0.810).

The one substantive divergence from production: the mirror computes both the submission's tokens and its audience-boost tokens from the raw gold `text`, while the live path computes submission tokens from `issuer + action + redacted_text` and the audience boost from the separately-extracted `submission.audience`. Officials likewise are scored on raw `text` vs. the service's `_submission_text` composition. The scoring *algorithm* is faithfully mirrored, but it runs over un-redacted, un-field-extracted inputs, so the measured rank idealizes the input side even though the ranking logic is exact. The harness docstring documents the audience-token choice as "a superset of any audience mention" but does not flag the raw-vs-redacted submission-text difference. It is not tuned in FinalSay's favor and misses are charged, but the measured rank should not be read as identical to what the live pipeline produces.

The seed fixtures were not touched anywhere in `b07ee6f..HEAD` (`git diff --stat -- 'seed/fixtures/**'` is empty), so the rank was measured against the same data as before, not gamed.

### Benchmark diversification without eval contamination

`generate_benchmark_triples` produces 308 triples by cycling the seven labels (44 each, perfectly balanced) and letting each annotator independently disagree with the gold on a fixed modular subset confined to genuinely confusable label pairs (A on `i%7==3`, B on `i%4==0`). It is pure — no RNG — so re-running yields identical triples and identical kappa. Verified directly: 308 pairs, kappa 0.625, `generate_benchmark_triples() == BENCHMARK_TRIPLES`, balanced gold distribution.

The per-pair display phrasing (`benchmark_pair_phrasing(i, gold_label)`) is index-driven and rotates issuers/topics/date-pairs/templates. It is stored only on the new nullable `BenchmarkPair.submission_text`/`official_text` columns, surfaced through `BenchmarkPairOut` and the reviewer UI, and — critically — never read by the harness (which pulls gold from `seed/fixtures`) or the kappa computation (which reads only the annotator label columns). The held-out temporal F1 remaining 0.048 and kappa 0.625 after the change is the empirical proof that the diversification did not leak into eval metrics. Seed idempotency holds: two consecutive seeds against a fresh SQLite DB yield 308 pairs / 616 annotations / zero null texts, and the `(i % 65, i % 120)` pairing produces 308 unique `(submission_id, official_id)` combinations (lcm 1560 > 308), so the natural-key guard never collapses two triples onto one row. The `official_id == official_id` → `official.id` change in the guard is a genuine correctness fix, not a weakening.

### HF run recorded as-is, mock stays the default

The HF blocks in `docs/eval-results.md` are internally consistent with a real run: all model-independent metrics (field F1, kappa, the four baselines, the entire time-to-identify table) are byte-identical to the mock blocks, and only the `finalsay` relationship row differs — exactly the footprint of swapping the ComparisonModel and nothing else. The recorded outcome is unflattering: HF institution F1 0.289 vs mock 0.739 and below the nli/prompted_llm baselines, temporal 0.143 vs mock 0.048, both at 0.000 false-confirmation with HF routing far more to unresolved (0.714). Reporting a worse number for one's own system is the clearest possible signal the numbers were not cherry-picked. Runtime (~33s / ~28s CPU-only) and setup (torch 2.14.0+cpu, transformers 5.16.1, ~1.6GB weights) are documented.

Mock remains the zero-setup default: `requirements.txt` untouched across the range, `get_comparison_model` returns `MockComparisonModel` unless `FINALSAY_COMPARISON_MODEL=hf`, the `from transformers import pipeline` is lazy inside `_ensure_pipeline` (never imported on the default path), opt-in deps isolated in `requirements-hf.txt`, and `.hf-cache/` gitignored.

### Report emitter refuses to fabricate — but can clobber

`--report`/`--report-all` write the full metrics table to markdown. `run_report_all` guarantees the offline mock blocks, then probes for the HF stack via `importlib.util.find_spec`; when absent it appends a clearly-labelled "HF … NOT EXECUTED … No numbers are fabricated" note rather than inventing values. The footgun: `--report-all` resets the document (`write_report(..., reset=first)`) on the first mock block, so running it in an HF-less environment overwrites the committed file and the real HF blocks are replaced by the note. A regen intended to refresh mock numbers would silently drop the measured HF results. Appending/merging or guarding the HF section would remove the hazard.

### Smoke test exercises the real pipeline, not stubs

`test_smoke_e2e.py` walks the full journey against the real ASGI app via `TestClient`: it provisions admin/issuer/student through the actual auth flow, publishes an official, submits a PII-laden conflicting notice, and asserts behavior that only holds if the pipeline works — original PII strings are absent and redaction masks present in both the API projection and a direct DB re-read of `Notice`/`NoticeField`; a candidate is retrieved and is the seeded official as top rank with positive score; the conflicting date drives a non-`consistent`, ungated label at confidence ≥0.6; the Merkle build produces a root over ≥2 leaves with a local anchor; verify returns ok/no-tamper and `?tamper=true` flips to detected; and a low-signal submission is gated to `unresolved` with a review case opened. These are behavioral assertions that fail on regression, not static-value checks. It is wired into both `make smoke` and `make test` (lives under `finalsay/tests`). The documented limitation — in-process rather than a live server because the sandbox reaps daemons between calls — is legitimate but means transport-layer concerns (real startup, CORS) are not covered by this target.

### Postgres path verified honestly

`docs/postgres-verification.md` records a genuine in-session run: `postgres:16-alpine` via podman, schema through `Base.metadata.create_all`, idempotent seed (identical counts across two runs, matching SQLite), and a targeted `pg_smoke.py` exercising submit/classify (a correctly gated `unresolved` at 0.40) and provenance build/verify with a tamper flip. The limitations are stated plainly rather than papered over: no compose runtime in the sandbox (a direct `docker run` was substituted for the committed `docker-compose.yml`), containers don't persist across tool calls, "migrations" means `create_all` not Alembic, and the pytest suite deliberately stays pinned to SQLite via `conftest.py`. `pg_smoke.py` is correctly excluded from pytest collection (no `test_` functions, non-`test_` filename). Nothing is claimed to run that wasn't run.
