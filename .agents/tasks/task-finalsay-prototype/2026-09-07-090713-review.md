# FinalSay prototype — cross-institution notice verification (backend + PWA)

The change lands the full FinalSay prototype: a synchronous FastAPI backend with a SQLAlchemy relational model, an OCR/redaction extraction pipeline, SHA-256 + daily-Merkle provenance behind a pluggable anchor, a single-step ComparisonModel with confidence gating to a reviewer queue, a two-annotator kappa benchmark, an idempotent synthetic seed for three institutions, a CLI evaluation harness with four baselines and two holdout splits, and a React/Vite PWA covering every actor. Defaults are offline (SQLite, mock model, local hash-chain anchor) so the demo needs no paid keys, and the swappable interfaces (`ComparisonModel`, `Anchor`, `InstitutionAdapter`) keep the opt-in HF/Polygon/live-fetch paths behind env vars. The six modules and four actors from `requirements.md` are all present and wired to reachable UI routes, temporal relations are stored as `relation_edge` rows (no graph DB), and the redaction-before-storage rule holds — only redacted text ever reaches the DB.

Watch for: (1) **`POST /api/auth/register` accepts an arbitrary `role`** — anyone can self-register as `admin`/`reviewer`/`issuer` and reach the protected routes (confirmed). (2) **The seed never builds a Merkle root**, so the student integrity check returns "no proof yet" on a fresh demo until an admin runs provenance build — a gap against acceptance A-2 (confirmed). (3) **The eval F1=1.000 is self-fulfilling**: the synthetic submissions are hand-crafted so the mock rule engine reproduces each gold label, so the harness measures the fixtures, not model skill (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The architecture is faithful to the spec's constraints. Feature switches in `config.py` default to `sqlite` / `mock` / `local`, and each opt-in path (`hf`, `polygon`) lazy-imports its heavy dependency so the default demo never needs `transformers` or `web3`. The three interfaces are genuine ABCs with a real default plus a real opt-in subclass, selected by `get_*` factories. Temporal relations are ordinary rows in `relation_edge`; there is no graph store anywhere.

Confidence gating never forces a guess: below the threshold the label is overridden to `unresolved` and a `review_case` row is created, including the no-candidate case, in both the service path and the harness. Redaction runs before any persistence — extraction redacts first, extracts fields from the redacted text, and only `redacted_text` + fields are written and hashed, so no unredacted original is ever stored.

The auth posture is the weak point. Routes are protected with a `require_role` dependency that re-reads the role from the DB, but registration lets a caller pick any role, which defeats the protection on admin/reviewer/issuer routes. For a synthetic demo this is survivable, but it is a real trust-boundary hole and R7.1 asks for role-appropriate protection.

Provenance is correct in isolation — proofs verify for every leaf including the odd-count duplicate path, tamper is detected for both the demo flag and real content mutation, the local anchor chains via `prev_hash` — but the daily root is never built during seeding, so the student-facing integrity check is inert until an admin action.

The evaluation harness computes all required metrics for all four baselines across both splits and exits 0 on success, but the perfect FinalSay scores reflect that the seed text was authored to trigger the mock rule engine's cues — the number demonstrates plumbing, not discrimination.

1. **Open role self-assignment** — `POST /api/auth/register` accepts any `role` in the payload, so an anonymous caller can register as `admin`/`reviewer`/`issuer` and reach every protected route. 3. **Self-fulfilling eval metrics** — synthetic submissions are crafted so the mock rule engine reproduces each gold label, making FinalSay F1=1.000 a measure of the fixtures rather than the model. Document this explicitly in the harness output/report, or add held-out pairs not authored around the rule cues.
4. **`leaf_index` uses `leaves.index(hash)`** — on duplicate content hashes (e.g. repeated `unresolved` submissions) this stores the first matching index rather than the notice's own. Proofs still verify because they are stored positionally via `zip`, but the persisted `leaf_index` metadata can be wrong; use the enumerate index instead.
5. **Fixture-keyed mock path is dead in production** — `MockComparisonModel(fixtures=...)` is only exercised in tests; `get_comparison_model()` and the harness both build it with no fixtures. Either wire seeded fixtures in or drop the unused seam, and correct the docstring that claims fixture-backed predictions exist.
6. **`POST /api/ingest/submit` is not student-gated** — it uses `get_current_user`, so any authenticated role can submit. Minor, but inconsistent with the per-actor route model; gate to `student` if that boundary matters.
7. **Alerts are client-only** — subscriptions persist in `localStorage` with no backend, so "subscribe to alerts" is per-browser and not durable. Acceptable for the prototype but should be called out as a stub in the UI/spec traceability.
8. **`sha256_notice` omits deadline/audience/action** — the canonical hash covers only issuer + date + redacted_text, so a targeted edit to only the deadline/audience/action columns would pass integrity verification even though they are displayed as evidence. <summary>Details</summary>

### Role self-assignment defeats route protection

`require_role` resolves the user from the bearer token, re-reads `role` from the DB (so the token's role claim is advisory, not authoritative), and 403s on mismatch. The hole is upstream: `register` copies `payload.role` straight onto the new `User` after only checking it is a member of `USER_ROLES`.

```python
if payload.role not in USER_ROLES:      # rejects garbage, not privilege
    raise HTTPException(422, ...)
user = User(..., role=payload.role, ...) # caller-chosen role
```

So the admin-only fetch/sources/provenance-build endpoints, the reviewer queue/resolve/benchmark endpoints, and the issuer publish endpoint are all reachable by anyone willing to register with the corresponding role — nothing stops a fresh registration from claiming `admin`. R7.1 ("role-appropriate routes SHALL be protected") is only half-met: the routes check roles, but roles are self-served. The cheapest fix is to force `role="student"` on public registration and create privileged accounts only via the seed or an admin endpoint.

### Provenance verifies, but the demo never builds a root

The Merkle math is correct and tested (odd-count duplicate path, simulated-tamper flag, real post-anchor mutation, `prev_hash` chaining), and `PolygonAmoyAnchor` falls back to local on any failure so it never blocks ingestion. The gap is lifecycle: `seed()` runs users → institutions → `fetch_all` → submissions → benchmark but never calls `build_daily_merkle`, and neither does `run_demo.sh`. So immediately after `make demo`, every notice lacks a `merkle_proof`, and the student's "Verify integrity" button hits the `proof_row is None` branch returning `ok=false, "no merkle proof stored; build the daily root first"`. The PWA degrades gracefully ("Ask an admin to build the daily root"), but acceptance A-2 (submit → result with confidence, evidence trail, and integrity check) is not satisfiable without an out-of-band admin step. Building the root at the tail of `seed()` (all seeded notices share the seed-run day) would close this.

One correctness nit in the same area: `leaf_index=leaves.index(notice.sha256)` looks up the *first* leaf whose hash equals this notice's hash. The seed generates multiple `unresolved` submissions from identical ambiguous text, producing identical hashes, so their leaves collide and the stored `leaf_index` points at the wrong position for all but the first. Verification is unaffected (proofs are stored positionally through `zip(notices, proofs)`), but the persisted index is misleading; iterate with `enumerate` and store the loop index.

### Canonical hash scope

`sha256_notice` hashes `issuer \n notice_date \n redacted_text`. Deadline, audience, and action are stored as separate notice columns and shown in the evidence trail, but are only covered by the hash insofar as they also appear inside `redacted_text`. For the seeded fixtures they do appear in the body, so tamper on those columns usually also changes `redacted_text` — but a targeted edit to only the `deadline` column would pass integrity verification. Either document that `redacted_text` is the sole source of truth for evidence, or fold the structured fields into the canonical form.

### The fixture-keyed mock path is dead

`classify_submission` gating is exactly GC-4 and the mock date reasoning guarantees the "22 Sept vs 15 Sept" pair is non-`consistent` (disjoint dates + postpone → `superseded`, + extend → `extended`, else `contradictory`). But the `fixtures` constructor arg on `MockComparisonModel` is only populated in tests: both `get_comparison_model()` and the harness instantiate `MockComparisonModel()` with no fixtures, so in every production and eval path the fixture-keyed branch is dead and classification is 100% rule-engine. The docstring's "uses fixture-keyed predictions when a pair matches a seeded fixture" overstates what the running system does.

### Evaluation harness measures the fixtures

The harness computes per-field extraction F1, relationship precision/recall/F1 via sklearn, false-confirmation rate, unresolved rate, and Cohen's kappa, for `finalsay` plus all four baselines (`chronological`, `page_change`, `nli`, `prompted_llm`), across `temporal` (bucket-1 holdout) and `institution` (Summit held out) splits, returning 0 on success — R6.1–R6.4 mechanically satisfied. The caveat: `dataset.generate_submissions` authors each submission's text specifically to trip the corresponding mock rule (the `superseded` sample contains "postponed and rescheduled to 22 Sep … earlier 15 Sep", the `cancelled` sample contains "cancelled"), and its docstring says so. So FinalSay's F1 of 1.000 reflects an evaluation set constructed around the model under test — a plumbing/round-trip check, not discrimination against realistic inputs, and the baselines being worse is likewise built in. State this in the printed report so a reader does not mistake it for model quality.

### Alerts subscription is a client-only stub

Every actor has a working route (student `/submit` `/result/:id` `/notices` `/alerts`; reviewer `/reviewer/queue` `/case/:id` `/benchmark`; admin `/admin/sources` with fetch trigger; issuer `/issuer/publish`), gated by both `ProtectedRoute` client-side and `require_role` server-side. The one caveat is `/alerts`: the feed pulls real `/api/notices` data, but subscription state lives in `localStorage` with no backend, so it is per-browser and non-durable — worth noting against "subscribe to alerts" rather than presenting it as a persisted subscription.
